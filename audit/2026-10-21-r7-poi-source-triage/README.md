# R7 / A05 Apache POI source impact triage — 21 October 2026

## Scope and source identity

Read-only source-flow review of the user-selected Kadrom repository snapshot at
`.dxa/a04-kadrom-source`, pinned to commit
`ae4aebbf8963f550f6bb7c3465fb1270d677af1c`. The supplied advisory match is
`org.apache.poi:poi-ooxml:5.3.0` → `GHSA-gmg8-593g-7mv3` / `CVE-2025-31672`,
with the supplied affected range `<5.4.0` and duplicate ZIP entry handling
during OOXML parsing as the concern. This note assesses whether the reviewed
application source reaches such a parser; it does not independently validate
the advisory record or prove exploitability.

No application, test, or container was run. No request was sent and no crafted
OOXML file was created or opened.

## Source flow

### POI dependency and production usage

- `hotelapp/pom.xml:28-33` declares `org.apache.poi:poi-ooxml:5.3.0` directly.
- The only POI usage found under `hotelapp/src/main/java` is
  `hotelapp/src/main/java/com/hotelapp/service/RosterService.java:14-23,165-166`.
  `toXlsx` creates a fresh `new XSSFWorkbook()` with no input stream or file,
  fills workbook objects from application data, and later writes to an in-memory
  output stream at `RosterService.java:211-220,228-229`. This is an OOXML
  generation path. No production
  import/parser API such as `WorkbookFactory`, `OPCPackage.open`, or
  `new XSSFWorkbook(InputStream)` was found in the reviewed application source.
- The generated file's request path is
  `hotelapp/src/main/java/com/hotelapp/controller/RosterController.java:32-46`.
  It is a GET endpoint, returns the generated bytes as an XLSX attachment, and
  has `@PreAuthorize("hasRole('BUSINESS_OWNER')")` at line 34. The service also
  checks that the listing's business owner ID equals the authenticated owner ID
  at `RosterService.java:67-75` before generation.
- `RosterEmailScheduler.java:40-57,64-90` also obtains XLSX bytes from the same
  roster generator and sends them to the listing owner. Its source flow does not
  accept workbook bytes as input to POI.

### Upload and file-processing paths

- The reviewed production controllers expose multipart upload routes for
  business logo/gallery images, candidate avatars, and conversation attachments:
  `BusinessController.java:93-99,120-127`,
  `CandidateController.java:99-105`, and `MessageController.java:105-114`.
  The reviewed controller tree contains no XLSX import/upload route.
- `FileStorageService.java:31-46,52-76` allows chat attachment extensions
  including `.docx` but not `.xlsx`; it stores the submitted bytes as a private
  raw Cloudinary object. Business and avatar routes use image-only extension
  allowlists at `FileStorageService.java:40-43,84-106,118-141`.
- The common upload validation at `FileStorageService.java:252-275` checks
  non-empty size, filename/path form, extension, then magic bytes. For DOCX,
  `FileStorageService.java:283-310` only checks the initial ZIP signature; no
  OOXML package is opened there. The chat upload path calls that storage method
  from `MessageService.java:295-307`; the reviewed source does not pass the
  uploaded bytes from that path into `RosterService` or another POI parser.
- Therefore an uploaded DOCX can be stored after the shallow signature check,
  but a source path from that upload to POI OOXML parsing is absent in this
  snapshot. Whether any external service or consumer later parses stored files
  is unresolved and outside this repository-only review.

### Tests

`hotelapp/src/test/java/com/hotelapp/service/RosterServiceTest.java:15-16,91-104`
and `:184-189,214-231` instantiate `XSSFWorkbook` on byte arrays returned by
the application's own roster generator, then assert sheet and cell contents.
These are generated-output checks, not tests that supply uploaded or otherwise
untrusted OOXML to the parser. No tests were run for this review.
